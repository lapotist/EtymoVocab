# EtymoVocab 模擬使用者瀏覽器測試

測試日期：2026-10-22。這次是三個獨立代理操作實際網站的情境測試，不是真實受試者研究；角色的感受與偏好是模擬推論。發現的操作結果、頁面文字、捲動距離與下載內容來自瀏覽器互動，程式碼僅用於診斷及修正。

## 方法與情境

每個代理使用獨立 Chromium context 與乾淨的網站資料，操作本機發佈站台的 `/EtymoVocab/` 路徑。開啟、選答、鍵盤操作、重新整理及下載均由瀏覽器執行。七日測試使用瀏覽器時鐘，並非實際等待七天。

| 模擬角色 | 瀏覽器工作 | 觀察範圍 |
|---|---|---|
| 台灣大學生，假設約 B1，390 × 844 手機 | 從總覽找第一課；答錯、高信心與筆記；跳過已知字；重練答對；回看結果 | 起步阻力、必填操作順序、回饋、修正後的進步呈現 |
| 英文教師，1280 × 900、Asia/Taipei | 選 re- 課；完成 repaint／resign；查原本的推論；匯出；檢查七日回訪；測 prelaunch 的語境不足題 | 課堂可用性、解說、作答證據與排程訊息 |
| 忙碌的鍵盤使用者，桌面及 320 × 650 | 用 Tab、Enter、方向鍵、Space 完成流程；未送出時重新整理及返回；查字後回練習；下載記錄 | 草稿與續作、鍵盤路徑、窄螢幕、資料保存預期 |

沒有執行真實螢幕閱讀器認證、真實裝置測試或學習成效實驗。窄視窗檢查不等同瀏覽器縮放認證。

## 驗證

- 學習記錄測試涵蓋首次／重練／已知跳過、版本隔離、七日門檻、跨分頁循序寫入與可讀匯出。
- 草稿測試涵蓋重新建立儲存物件後恢復、題目／階段隔離、資料驗證、送出後清除與儲存不可用時的記憶體降級。
- 三個原角色均在修正後重新操作瀏覽器並通過指定工作。手機角色確認重練後首次成績不變、最近結果顯示答對，展開作答歷史不增加記錄。教師確認重新整理仍可回看解說；用瀏覽器時鐘在開放前 1 毫秒仍鎖定、開放當下解鎖，延後題的作答歷史和可讀匯出也通過。
- 鍵盤角色用純鍵盤選答、填信心與筆記；重新整理及 Back／Forward 能恢復草稿，送出只產生一次作答並清除草稿，下一題顯示 2/2。拒絕 sessionStorage 的情境仍能作答並顯示降級提示。
- 最終新分頁測量：390 × 844 的推薦按鈕為 y=403–453；320 × 650 為 y=462–537，兩者初始畫面均可完整看到按鈕，頁面沒有水平溢出。學習送出按鈕至少 44px 高。
- 手機重測另外發現新回歸：條件式的頂層空節點曾被渲染成 `null` 文字。已在畫面更新函式排除空節點；兩個尺寸的最終瀏覽器測試確認沒有殘留文字。
- 37 項 JavaScript 測試通過（22 項作答記錄、9 項草稿、3 項教材、3 項地圖），Release 靜態站台建置成功。沒有修改 C# 查詢邏輯。
- 必填表單與回饋在手機上仍需要捲動。選填筆記收合後，390px 首題頁面由約 1509px 降到 1444px；這不代表所有重要控制都能在第一個畫面看到。

## 可重複的瀏覽器工作

1. 使用乾淨的 390 × 844 或 320 × 650 context 開啟 `#/learn`，確認推薦按鈕在初始畫面內，沒有空成績儀表板或水平溢出。
2. 開一課，選擇不熟悉，選答案、信心並填筆記。在送出前重新整理，再 Back／Forward，確認輸入仍在且尚無正式作答。
3. 刻意答錯第一題、跳過第二題。完成後展開歷史，檢查原答案、信心、筆記、解說與來源；記錄數不應改變。
4. 重練第一題答對。確認首次分數不變，最近練習另顯示答對。展開歷史後，不得額外新增一次作答。
5. 用測試時鐘跳到 `dueAt - 1ms` 與 `dueAt`，重新整理回訪頁，確認門檻與畫面上的當地日期／時間／時區一致。作答後再回看延後題歷史。
6. 實際下載匯出檔，確認有可讀的題目與答案，且儲存中的作答沒有混入匯出專用的欄位。對禁止 sessionStorage 的 context 重複一次基本作答，確認能降級而不中斷。

## 暫緩的建議

教師希望課程有先備知識與時間估計；學生希望非目標字有可選的詞義或發音支援。這些需求尚未經真實學習者確認，不應直接推成已驗證的難度分級。可先小規模試用，再考慮額外提示及不帶策略提示的練習題。

匯入還原、日曆提醒、全站一致的路由焦點管理及公開教師報表仍未提供。本次不改變教材題目、答案、課程版本或原有計分規則。

## 2026-10-24：詞源圖、批次查詢與獨立收藏

依使用者修正，地圖移除同義／反義分支，只保留祖源、構詞、詞根字族及詞條明列的 doublet；同反義詞改由單字探索及 `#/bulk` 掃描，選中的字放入 `#/saved` 收藏，不把收藏當成詞源證據。

三個代理以獨立 Chromium context 實際操作新介面。固定引擎回應的 UI 測試涵蓋混合成功／空關係／404、重複與片語輸入、超過 20 筆、結果順序、篩選、收藏與重新整理、移除、JSON 下載、禁止儲存、首次寫入額度失敗，以及 390px／320px 無水平溢出。

這些操作找到三類介面缺陷並修正：停止按鈕原本要等舊請求結束才釋放控制；主查詢及限流後立即停止曾可繞過等待；第一次寫入失敗後的收藏提示沒有立即更新。修正後實際重測確認：停止後可立即操作，舊回應不影響新批次；收到限流時就記錄期限，停止或重查都遵守它，並可恢復被限流及未完成項目；寫入失敗立即告知且仍能匯出本次記憶體收藏。

另以發佈站台的真實 WebAssembly 引擎驗證七組工作，只攔截 Wiktionary HTTP 回應為倉庫記錄的 12 個詞條及固定分類清單，不替換 `engine.js`。結果包括：nice 在樹外呈現 24 個同義詞與 21 個反義詞連結；hotel 自動顯示 hostel／hospital 的同源關係；inspect 的詞根可加入 spectacle；批次 nice、bank、inspect 去重並逐筆顯示；由單筆及批次選入的 charming／delightful 在收藏頁重新整理後仍在。這些檢查不代表即時上游永遠可用。

可重複的 UI 回歸檢查保存在 `tests/browser/discovery.browser.mjs`，以 `npm run test:browser` 執行，需另有 Playwright／Chromium。它使用固定引擎回應操作真實 DOM；完整 .NET 詞典解析由另一組測試與上述發佈引擎檢查覆蓋。

## 2026-10-24：搜尋效能

保留每次 20 字的介面上限，改以 5 字一組預取起始頁，最多兩組同時進行；共用原形頁，完整解析結果保留於有限的分頁快取。畫面只更新變動的結果卡。

真實發佈版 WebAssembly 的前後比較使用同一份記錄的 nice 詞條，複製為 20 個獨立測試標題，HTTP 回應固定延遲 180ms，總計 900 個可收藏詞按鈕。這是本機固定條件測量，不是即時 Wiktionary 速度承諾：

| 測量 | 改善前 | 改善後 |
|---|---:|---:|
| 首次 20 字全部完成 | 2708ms | 951ms |
| 字典 HTTP 請求 | 20 | 4 |
| 重複同一組 20 字 | 280ms | 21ms |
| 第一筆結果出現 | 293ms | 436ms |
| 單字直接重查 | 30ms | 0.1ms |

首次結果略晚，但第一組會同時提供最多 5 個字，整批完成時間約減少 65%。原形追查、網路、裝置及實際詞條大小會影響結果；第一次單字查詢的耗時沒有明顯改變，不能把快取改善描述成所有查詢都立即回應。

另一個只測介面更新成本的密集案例有 20 字、2000 個候選詞，各跑三個乾淨 context：串流回呼／繪製 CPU 中位數由約 239ms 降至 86ms；已完成卡片的替換次數由 210 次降至 0。瀏覽器回歸測試確認新結果到達時，已完成卡片及其中鍵盤焦點保持不變，篩選與收藏仍正確更新。

改善後通過 111 項 .NET 測試、84 項 JavaScript 測試、6 組介面瀏覽器回歸與 4 組真實發佈引擎回歸。真實引擎檢查另外確認不可變快取仍可建立詞源圖及展開來源、Sugar／sugar 大小寫不混淆、已快取的批次不再發出 HTTP，以及實際上游 429 回應產生的等待資訊在停止／重查時仍受遵守。
